KYB Data Source and Consumption Strategy
1. Purpose
This document captures the current understanding and proposed approach for consuming branch hierarchy, workforce, nearby-branch, and BDIS/device data for KYB.

The intent is to document the proposed rules and responsibilities so that the KYB team can review and agree on the design before engaging the respective source teams.

2. Branch Manager Hierarchy
Sources involved
Two sources are relevant:

Workforce

BLDS

Workforce
Workforce should be treated as the authoritative source of truth for the current manager/role relationship.

It determines who is actually assigned to a branch and what role they hold.

BLDS
BLDS provides branch-related data and updates, but BLDS has explicitly indicated that it is not the authoritative source for branch hierarchy.

Therefore, BLDS should not be treated as the final source of truth for determining the current branch manager.

Proposed approach
KYB should use Workforce as the authoritative source for manager/role information and use BLDS where its branch data/update information is required.

The exact consumption mechanism, including Kafka subscription and any existing KYB data feed that can be reused, should be confirmed during the design review.

3. Nearby Branches
KYB requires nearby-branch information as a separate use case.

The current understanding is that an existing REST API is available for this purpose.

Proposed approach:

KYB → Existing Nearby Branch REST API → Nearby Branch Information

The API contract, response fields, latency, refresh requirements, and expected volume should be confirmed before implementation.

4. BDIS Device Data
BDIS currently has multiple mechanisms through which its data can potentially be consumed:

Kafka

Snowflake

Databricks

Data Lake

The current direction is to consume the required BDIS/device information through the Data Lake.

The currently identified BDIS use case includes TCR/device-related information required by KYB.

5. BDIS Refined Data Strategy
A concern with directly querying large/raw BDIS datasets is scalability.

KYB may eventually need information for multiple devices per branch. The volume could therefore increase significantly if KYB performs repeated queries against raw data.

Proposed strategy
Instead of having KYB repeatedly query the raw dataset:

KYB identifies the exact fields required from BDIS.

BDIS creates/maintains a refined dataset/table containing only those required fields.

BDIS periodically refreshes this refined dataset from its underlying Data Lake/data sources.

KYB consumes the refined dataset.

KYB can then persist only the information required for its own application use cases, rather than duplicating the complete raw BDIS dataset.

Conceptually:

BDIS Raw/Data Lake → BDIS Transformation/Query → Refined KYB Dataset → KYB

Benefits
Reduces raw-data duplication.

Reduces network traffic.

Reduces query load on KYB.

Avoids KYB repeatedly processing large datasets.

Allows BDIS to optimize the extraction/query logic close to the source.

Makes refresh frequency configurable.

Provides a cleaner contract between BDIS and KYB.

6. Important Scalability Consideration
The design should not assume that each branch has only one or two devices.

The solution should support scenarios where a branch may have approximately 10–15 devices or potentially more.

The following should therefore be confirmed:

Expected number of devices per branch.

Total number of branches.

Expected total device volume.

Required refresh frequency.

Expected concurrent KYB reads.

Whether the refined table can support the expected query volume.

Whether indexing/partitioning is required.

Whether the refined dataset should be branch-keyed and/or device-keyed.

Retention requirements.

SLA/latency expectations for data freshness.

The goal should be to avoid unnecessary duplication while still meeting the real-time requirements of the Branch Manager experience.
