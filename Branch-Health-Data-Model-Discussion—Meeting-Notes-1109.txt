## 1. Purpose

Define scope and approach for the Branch Health near-real-time data store and determine what's needed to build the high-level logical data model/schema.

The broader architecture supports Know Your Branch (KYB), Branch Health, Branch Analytics, and other future use cases under a common SEAL, with a two-database approach. **Immediate priority is Branch Health** — KYB analytics issues and future requirements will not drive the current data-modeling exercise.

---

## 2. Overall Architecture — Single SEAL, Two Databases

### Database 1 — Near-Real-Time Database
- Aurora PostgreSQL Global
- Source of Record (SOR) for Branch Health near-real-time data
- Supports the Branch Health dashboard and its near-real-time APIs
- Retention: ~6 months; data beyond that is purged per retention policy

### Database 2 — Analytics Database
- Aurora PostgreSQL Global
- For analytical and historical use cases
- Retention: ~2 years
- Primary source: Data Lake (current latency ~4–5 hours)
- If a required dataset isn't in the Data Lake, selected data may be moved from Near-Real-Time DB → Analytics DB

**Key principle:** Replication to Analytics is **use-case driven**, not automatic. Not all near-real-time data gets replicated.

## 8. Near-Real-Time Data

Examples: application analytics, transaction values/counts, operational/application health, other event-driven metrics.

- Some metrics need availability within **~15 minutes**
- Some require time-windowed aggregation (5-min, 15-min, or other defined windows)

Model must distinguish **current state/event data** from **time-windowed aggregated metrics**.

---

## 9. Analytics / Non-Near-Real-Time Data

Examples: OSAT scores, OSAT categories/subcategories, Chase sales, other business/sales analytics.

Freshness is **not necessarily "daily" by default** — each metric needs an explicit maximum acceptable age (≤15 min / hourly / 4–5 hrs / daily / weekly / monthly). Data shouldn't be allowed to go stale just because it's labeled "analytics."

## 15. Data Lake & Analytics DB Paths

---

## 16. Replication Principle

> Do not move the entire Near-Real-Time dataset into Analytics simply because it exists there.

Only data with an actual downstream requirement gets persisted to Analytics. Keeps Analytics focused, avoids unnecessary data movement/storage.

**Example — BLDS:** Branch Health needs it in Near-Real-Time DB; KYB/Analytics may also need it in Analytics DB. If not available via Data Lake, it can be transferred from Near-Real-Time → Analytics at the agreed cadence. This is a per-dataset decision, not a blanket rule.

## 18. Data Retention

| DB | Retention | Notes |
|---|---|---|
| Near-Real-Time | ~6 months | Purge/delete after 6 months (not a simple truncate); required historical data must already exist in Analytics before purge |
| Analytics | ~2 years | Only required datasets persisted |

No separate hot/cold storage tier was established within the Near-Real-Time DB. Confirmed requirement: 6-month retention → purge.

```
Source Systems
      ↓
Near-Real-Time DB (6 months)
      │
      ├──→ Selected data → Analytics DB (2 years) → Historical use cases
      │
      └── After 6 months → Purge
```

Action: identify which datasets need historical retention **before** they hit the 6-month purge point.

## 25. Scope Statement (for top of project documentation)

> Current Scope: Develop a high-level logical data model for the Branch Health Near-Real-Time Database, supporting both the All Branches and Single Branch Branch Health experiences. The model will be based on confirmed Branch Health domains, entities, relationships, source systems, and freshness requirements. Near-real-time requirements, particularly metrics requiring approximately 15-minute freshness, will be clearly distinguished from data that can be refreshed less frequently. KYB Analytics, existing KYB field mapping, and broader Analytics database requirements are outside the current modeling scope and will be addressed separately as future use cases where applicable.
