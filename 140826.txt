3. Required Actions

Required Actions are primarily an urgency signal.

Some actions have an actual completion window, for example actions that must be completed within approximately 48 hours.

Other actions do not have a hard due date. They are aging-based and should simply not be allowed to reach an undesirable aging threshold.

Do not treat every outstanding item as having a hard due date.

Required Actions tile

The tile should remain visible even when there are no urgent items.

Examples:

- "0 items due"
- "2 items due today"
- "3 items due tomorrow"
- "5 items"

Use an urgency waterfall.

The tile should show the most urgent applicable state rather than displaying every urgency bucket simultaneously.

Do NOT create a tile such as:

"2 today · 3 tomorrow · 5 aging · 4 upcoming"

That makes the tile too complicated and reduces the urgency signal.

Instead:

- If items are due today, show those.
- Otherwise show the next applicable urgent deadline.
- If there are no hard deadlines but there are outstanding items, show the outstanding count without incorrectly calling them "due."

Important distinction

Use these concepts separately:

- Due today
- Due tomorrow / upcoming
- Outstanding
- Aging

Do not invent a due date for an aging-only item.

Detailed Required Actions view

When the user clicks Required Actions, take them to the detailed dashboard/action experience.

The detailed view should show the complete set of relevant items, including:

- Urgent items
- Upcoming items
- Aging items
- Status
- Due date where applicable
- Aging threshold where applicable
- Priority
- Action/take-action capability
- Relevant branch details

Users should be able to work ahead even when an item is not currently represented as the highest urgency on the tile.

4. Control Exceptions

Control Exceptions are a separate, high-priority experience.

Do not combine them with Required Actions.

The Branch Manager should see a separate Control Exceptions tile/entry when applicable.

Clicking it should take the user to the existing Control Exceptions experience where they can:

- View unresolved exceptions
- View branch exceptions

- See status/date information
- Take action to resolve an exception

The current reference design shows Control Exceptions as a separate tab/area from Branch Dashboard action items.

5. Completion and data freshness

Do not assume that completion status is always real time.

A Branch Manager may complete an item in another system and return to Branch Health before the source system has updated or propagated the completion.

Therefore the dashboard may temporarily continue showing an item as outstanding.

For every data source, determine:

- System of record
- Integration mechanism
- Update cadence
- Expected latency
- Completion-status latency
- Dashboard refresh requirement

Where necessary, the UI can communicate that completion status may take time to update.

Do not promise real-time status if the source does not support it.

Manual completion

Do not automatically add a generic "Mark Complete" action.

The official completion state should come from the system of record.

If a future requirement needs a user acknowledgement, it should be represented separately, for example:

"Completed by user - Awaiting system confirmation"

It must not overwrite the official source-system status.

Do not assume clicking means every individual notification was actually read.
